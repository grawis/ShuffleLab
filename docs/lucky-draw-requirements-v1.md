# Lucky Draw 抽籤網站：Codex 實作需求規格 v1.0

## 1. 專案目標

建立一個純前端、無需登入即可使用的抽籤網站，主要使用情境為課堂、報告順序、活動抽獎、聚會及隨機分組。

參考網站：https://www.zhtoolbox.com/tools/lucky-draw

參考網站只用於理解功能與操作流程。請自行設計程式架構、介面與視覺風格，不得複製其原始碼、文字、圖片、商標或版面。

第一版應做到：功能完整、操作直覺、桌機與手機皆可使用，並可部署至 GitHub Pages。所有資料只在使用者瀏覽器內處理，不上傳伺服器。

## 2. 建議技術

- React
- TypeScript
- Vite
- CSS Modules、一般 CSS，或輕量 CSS 方案；不要為了此專案加入過重的 UI 框架
- Vitest：測試亂數、抽籤、分組、名單解析等核心邏輯
- localStorage：保存歷史紀錄與必要偏好
- Web Crypto API：產生亂數
- GitHub Actions：建置並部署至 GitHub Pages

除非確有必要，第一版不使用後端、資料庫、帳號系統或付費服務。

## 3. 第一版功能範圍

網站包含四種模式：

1. 數字抽籤
2. 名單抽籤
3. 團體分組
4. 順序抽籤

各模式共用一致的導覽、輸入風格、結果呈現與歷史紀錄設計。

## 4. 共通操作流程

1. 使用者選擇模式。
2. 輸入數字範圍或名單。
3. 調整該模式的設定。
4. 系統即時驗證輸入並顯示有效項目數量。
5. 使用者按下開始按鈕。
6. 顯示短暫的滾動／洗牌動畫。
7. 動畫停止後顯示正式結果。
8. 顯示簡單的彩帶或慶祝效果；應尊重作業系統的 `prefers-reduced-motion` 設定。
9. 將正式結果加入歷史紀錄。
10. 使用者可全螢幕查看或匯出 PNG。

動畫只負責呈現，真正結果必須在動畫開始前由抽籤核心決定，不能以動畫最後一幀當作抽籤結果。

## 5. 模式一：數字抽籤

### 輸入與設定

- 最小整數
- 最大整數
- 抽取數量
- 允許重複／禁止重複
- 即時顯示可用數字總數

### 規則

- 最小值不得大於最大值。
- 僅接受安全範圍內的整數。
- 禁止重複時，抽取數量不得大於範圍內可用數字數量。
- 允許重複時，同一數字可在同一次結果中出現多次。
- 錯誤時顯示具體原因，並停用開始按鈕。

## 6. 模式二：名單抽籤

### 輸入與設定

- 手動輸入名單
- TXT 匯入
- CSV 匯入
- 抽取人數
- 允許重複／禁止重複
- 即時顯示有效項目數量

### 手動名單解析

- 基本格式為一行一個項目。
- 移除每行前後空白。
- 忽略空白行。
- 第一版保留重複名稱，但要顯示「發現重複項目」提示；不要未經同意自動刪除。
- 原始輸入仍須保留，避免資料清理後使用者無法修改。

### 抽取規則

- 禁止重複時，同一次抽籤結果不得出現相同的名單項目。
- 如果使用者再次抽籤，第一版仍以完整名單重新抽取；不自動永久移除前次抽中者。
- 禁止重複且抽取數量超過有效項目數時，不可開始抽籤。

## 7. 模式三：團體分組

### 輸入

- 使用和名單抽籤相同的手動、TXT、CSV 輸入系統。

### 分組方式

使用者可擇一：

1. 指定組數
2. 指定每組人數

### 規則

- 先以安全亂數將全部項目洗牌，再依序分配。
- 指定組數時，各組人數差距最多為 1。
- 指定每組人數時，依指定容量建立足夠組別；最後一組可以人數較少。
- 每個項目只能被分配一次，不可遺漏或重複。
- 結果顯示組別名稱、每組人數及組員清單。
- 第一版組名使用「第 1 組、第 2 組……」，暫不加入自訂組名、同組或不同組限制。

## 8. 模式四：順序抽籤

### 輸入

- 使用和名單抽籤相同的手動、TXT、CSV 輸入系統。

### 規則

- 使用安全的洗牌演算法，將全部有效項目隨機排序。
- 每個項目在結果中恰好出現一次。
- 顯示完整編號順序，例如：

```text
1. 林小美
2. 王小明
3. 陳小華
```

- 適用於報告、上台、比賽、面試或遊戲順序。

## 9. TXT 匯入

- 接受 `.txt` 檔案。
- 以 UTF-8 為主要編碼。
- 依「一行一個項目」解析。
- 套用與手動名單相同的空白行及前後空白處理。
- 解析後先顯示或填入名單輸入區，讓使用者可再修改，不要立即開始抽籤。
- 檔案無法讀取或內容為空時，顯示明確錯誤。

## 10. CSV 匯入與預覽

CSV 匯入是本專案相較一般抽籤網站的主要改善功能之一。

### 10.1 基本流程

1. 使用者選擇 `.csv` 檔案。
2. 系統解析 CSV，正確處理引號、逗號、換行及空白儲存格；不要只用 `split(',')`。
3. 開啟 CSV 匯入預覽視窗。
4. 顯示檔名、資料表格與解析結果。
5. 使用者選擇標題列、欲匯入的欄，以及欲匯入的資料列。
6. 系統即時顯示預計匯入幾筆。
7. 使用者確認後，將資料轉為名單項目並加入／帶入目前模式。
8. 使用者可取消，取消時不得更動目前名單。

### 10.2 標題列

- 預設將第一列視為欄位名稱。
- 提供「第一列是標題」勾選項。
- 若取消，欄位名稱顯示為「欄 1、欄 2……」，第一列視為一般資料。

### 10.3 欄（Column）選擇

- 每個欄位都有勾選框。
- 提供「全選欄位／取消全選」控制。
- 至少選擇一欄才能確認匯入。
- 表格應清楚標出已選欄位。

### 10.4 列（Row）選擇

- 每筆資料列都有勾選框。
- 提供「全選資料列／取消全選」控制。
- 至少選擇一個有效資料列才能確認匯入。
- 第一版不需要複雜的篩選器，但表格較長時應可捲動，並保持表頭可辨識。

### 10.5 多欄位合併規則

- 同一資料列中，被選取的多個欄位必須合併成「一個抽籤項目」，不能拆成多個候選項目。
- 預設顯示順序依 CSV 原始欄位順序。
- 預設分隔符號為 `｜`。
- 例如選擇「姓名」和「學號」後：`王小明｜A001`。
- 忽略該列中被選欄位的空白儲存格。
- 如果某一列選取欄位全為空白，該列不匯入，並在預覽中提示。

### 10.6 預覽與安全性

- 預覽區顯示實際表格，不執行儲存格中的 HTML 或公式。
- 對過大的檔案設定合理上限並顯示說明，避免瀏覽器卡死。可由實作者提出合理預設值並寫入 README。
- CSV 內容只在本機瀏覽器解析，不上傳伺服器。
- 解析錯誤時保留原本名單，並顯示使用者看得懂的錯誤訊息。

## 11. 亂數與公平性

- 使用 `crypto.getRandomValues()`，不要使用 `Math.random()`。
- 整數抽取須以 rejection sampling 避免 modulo bias。
- 名單抽取、隨機排序與分組使用 Fisher–Yates shuffle，亂數來源同樣使用 Web Crypto API。
- 將亂數與抽籤邏輯放在獨立的純函式模組，不與 React 畫面耦合。
- 介面可簡短標示「使用 Web Crypto API 產生亂數」。不要宣稱具有政府抽獎、公證或法律層級的公平性認證。

## 12. 結果顯示

- 各模式使用適合的結果版型：數字、多名得獎者、分組卡片、完整順序清單。
- 支援全螢幕結果模式。
- 支援將目前結果匯出為 PNG。
- 匯出圖片應包含模式名稱、結果及產生時間；不應包含輸入控制項。
- 若瀏覽器不支援全螢幕或圖片匯出失敗，顯示可理解的替代提示。
- 結果文字應可選取，並提供「複製結果」按鈕；這是低成本且實用的基本功能。

## 13. 歷史紀錄

- 每次完成正式抽籤後建立一筆紀錄。
- 每筆至少包含：唯一 ID、模式、結果、建立時間，以及足以重新顯示結果的設定摘要。
- 使用 localStorage 保存，重新整理頁面後仍存在。
- 提供查看歷史紀錄與清除全部紀錄。
- 清除前需再次確認。
- 設定合理保存上限，例如最近 50 筆；超過時移除最舊紀錄，並在 README 說明。
- 第一版不實作雲端同步、跨裝置同步或登入。

## 14. 介面與易用性

- 支援 Desktop、Tablet、Mobile。
- 主要功能不應依賴 hover 才能操作。
- 使用清楚的繁體中文標籤及錯誤訊息。
- 模式切換明確，切換前若可能清除尚未使用的輸入，應保留共用名單或先提示。
- 按鈕需有 disabled、loading／動畫中、focus 狀態。
- 動畫進行時避免重複觸發抽籤。
- 表單控制項需有可讀的 label；鍵盤可操作；色彩對比合理。
- 尊重 `prefers-reduced-motion`。
- 首版可採明亮、簡潔、帶有活動感的原創設計；不需模仿參考網站。

## 15. 狀態與資料原則

- 四個模式切換時，名單型模式共用目前名單，避免使用者重複貼上。
- 數字抽籤設定獨立保存於前端狀態。
- 抽籤中的暫時動畫內容不可寫入歷史。
- 重新抽籤會產生新結果及新歷史紀錄。
- 重新整理後至少保留歷史紀錄；是否保留草稿名單可由實作者選擇，但須在 README 說明，且不可將資料送出瀏覽器。

## 16. 錯誤處理

至少處理以下情況：

- 名單為空或清理後無有效項目
- 抽取人數不是正整數
- 禁止重複時，抽取數量超過候選數量
- 數字最小值大於最大值
- CSV／TXT 副檔名或內容不符
- CSV 格式無法解析
- CSV 未選欄、未選列或選取結果皆為空
- 檔案過大
- localStorage 無法使用或容量不足
- 全螢幕 API 或 PNG 匯出失敗

錯誤訊息應說明問題及修正方法，不要只顯示 `Error`。

## 17. 程式架構要求

- 不要把所有程式放在 `App.tsx`。
- UI 元件、模式設定、檔案匯入、結果顯示、歷史紀錄與核心演算法應合理分離。
- 建議目錄概念如下，可依實作調整：

```text
src/
├─ components/
├─ features/
│  ├─ number-draw/
│  ├─ name-draw/
│  ├─ grouping/
│  ├─ order-draw/
│  ├─ import/
│  ├─ results/
│  └─ history/
├─ utils/
│  ├─ secureRandom.ts
│  ├─ shuffle.ts
│  └─ parsers.ts
├─ types/
├─ App.tsx
└─ main.tsx
```

- 核心資料型別要清楚定義，避免大量使用 `any`。
- React 元件不要自己重新實作亂數演算法。
- 外部套件應保持精簡；如需 CSV 解析或 PNG 匯出套件，選擇成熟且維護中的方案，並在 README 說明用途。

## 18. 測試與品質要求

至少為以下核心行為建立自動化測試：

- 安全亂數整數的邊界正確
- Fisher–Yates 結果不遺漏或新增項目
- 禁止重複的抽取不會重複
- 數字範圍與抽取數量驗證
- 指定組數時各組人數差距最多為 1
- 指定每組人數時所有項目皆恰好出現一次
- 順序抽籤包含所有輸入且各出現一次
- 手動名單的空白清理
- CSV 多欄位合併、空白列與標題列處理

完成前請執行並修正：

```bash
npm run lint
npm run test
npm run build
```

若專案模板沒有 lint script，請建立合理的 ESLint 設定，不要略過。

## 19. README 要求

README 至少包含：

- 專案簡介與功能
- 隱私說明：資料僅在瀏覽器本機處理
- 技術棧
- 本機安裝與執行方式
- 測試與建置指令
- CSV 匯入格式與多欄位合併規則
- 檔案大小／列數等實作限制
- localStorage 保存內容與歷史上限
- GitHub Pages 部署方式
- 已知限制及後續可擴充項目

## 20. GitHub Pages 部署

- 專案應能由 GitHub Actions 自動部署至 GitHub Pages。
- 正確處理 Vite 在專案型 GitHub Pages 網址下的 `base` 路徑。
- Push 到預設分支後執行測試與建置；成功後才部署。
- 不將 secrets、個人資料、建置產物或 `node_modules` 提交到 Git。
- 提供合適的 `.gitignore`。

## 21. 第一版不做的功能

以下項目明確排除，避免範圍膨脹：

- 後端、資料庫、登入、會員系統
- 雲端同步或多人即時協作
- 多獎項抽獎
- 權重抽籤
- 抽過者跨次自動排除、Undo
- 儲存多份常用名單
- 團體分組的指定同組／不同組限制
- 自訂組名
- 音效與複雜主題系統
- PWA、離線安裝
- 多語系

以上可在 v1.0 穩定後再討論。

## 22. 驗收條件

第一版完成需同時符合：

1. 四種模式皆能完成有效操作並得到正確結果。
2. 手動輸入、TXT 與具欄／列選擇預覽的 CSV 匯入可用。
3. 所有正式亂數均來自 Web Crypto API，且整數映射無 modulo bias。
4. 結果可全螢幕、複製並匯出 PNG。
5. 歷史紀錄可保存、重新載入、查看與清除。
6. 桌機與手機版沒有明顯溢位或無法操作的控制項。
7. 常見錯誤輸入均有明確提示且不造成頁面崩潰。
8. 核心測試、lint 與 production build 全部通過。
9. README 完整，並可依步驟在乾淨環境啟動。
10. GitHub Pages 部署流程已設定。

## 23. 給 Codex 的執行指示

請先檢查目前資料夾內容與 Git 狀態，再進行實作：

1. 如果資料夾是空的，建立 React + TypeScript + Vite 專案。
2. 如果已有專案，先閱讀既有程式與設定，不要覆蓋使用者現有內容。
3. 先提出簡短的分階段實作計畫，再開始修改。
4. 依照「核心亂數與資料模型 → 四種模式 → CSV 預覽匯入 → 結果與歷史 → 響應式與無障礙 → 測試 → GitHub Pages」順序完成。
5. 遇到需求未明確的地方，採用最簡單且符合本規格的方案；若選擇會明顯影響使用方式，再詢問使用者。
6. 每完成一個階段，執行相關測試，並說明修改內容。
7. 不自行增加第 21 節排除的功能。
8. 完成後提供：變更摘要、執行指令、測試結果、目前限制、部署前還需由使用者完成的 GitHub 設定。
